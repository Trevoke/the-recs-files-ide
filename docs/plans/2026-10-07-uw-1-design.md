# Design: UW-1 Turn record changes into code

Implementation-level decisions for the first slice. Nothing here is a record,
and code does not cite this file; what code needs to justify itself against is
in `docs/`.

Records this design serves:

- UW-1: Turn record changes into code
- ADR-1: Ship the IDE as a bare Emacs with its own pinned binary
- ADR-2: Talk to machines over ACP

## Scope of the first slice

In: opening a target product's records in the IDE, and every step and
extension of UW-1.

Out: the background machines that look after records, any record editing beyond
plain org-mode, and packaging the IDE for other people (ADR-1 is followed during
development by running the local Emacs 30 with the IDE's configuration
directory).

## How the IDE is arranged

The IDE is an Emacs configuration directory in this repository, launched as
`emacs --init-directory=<this repo>/<config dir>` against a target product.
Its elisp is split by job:

| Job | Serves |
|---|---|
| Read the target product's AGENTS.md for its projection paths | UW-1 precondition |
| Find the record changes: `git diff <implemented ref>..HEAD` under the projection paths, plus uncommitted edits, each change named by its record's identifier and title | UW-1 steps 1–2, 2a |
| Define machines as data: instructions, devices, working directory; shipped with the IDE, overridable per target product | UW-1 steps 3, 5 |
| Run machines over ACP (through `agent-shell` or the ACP library under it), and notice when one finishes or stops | UW-1 steps 3–5, 3a, 5b |
| Drive UW-1 step by step | UW-1 |

Elisp names use the prefix `trf` (the-recs-files).

## Decisions the design makes

These were proposed as architectural decisions and not taken up as records;
they hold for this slice and may be revisited.

1. **Most of the IDE's work is given to machines** — instructions and devices —
   and the elisp does what instructions cannot: reading git, running ACP
   sessions, opening buffers.
2. **The reconciliation assessor is a different machine from those of the
   implementation workflow**, so the record implementation report is not an
   account of the work by the machines that did it.
3. **The implementation workflow works in a git worktree**, under a directory the
   target product's `.gitignore` holds; the worktree is the work in progress of
   UW-1 *a, 3a and 6a.
4. **Implemented record changes are marked with a git ref**
   (`refs/recs/implemented`), moved at UW-1 step 7 to the commit the record
   changes were taken from.
5. **The IDE keeps its state in git and files only** — the ref, the worktree,
   the record implementation report as an org file in the worktree — so a
   restart loses nothing and machines read what the IDE reads.

## UW-1, step by step

1. The record keeper runs the IDE's command to implement the record changes.
2. The IDE lists the record changes in a buffer, each by identifier and title;
   the record keeper confirms. None: the IDE says so (2a; text goes to the
   message catalog).
3. The IDE creates a worktree and runs the implementation workflow there over
   ACP: the brainstorming machine, then the planning machine, then the
   executing machine, each with instructions naming the record changes and its
   skill among its devices.
4. Each machine's questions arrive in its session buffer; the
   record keeper answers there.
5. When the executing machine finishes, the IDE starts the reconciliation
   assessor in the same worktree, with devices that read the code and run the
   tests and none that edit. Its instructions: for each record change, find the
   tests that cite it, run them, and write the record implementation report in
   a fixed org shape. Which tests cite a record is the machine's to find.
6. The IDE opens the record implementation report beside the record changes.
7. Accept: the IDE merges the worktree's branch and moves the ref. Reject (6a):
   the worktree stays.

Extensions: *a closes the machines' sessions and keeps the worktree. 3a shows
why the machine stopped and offers to start it again on the same worktree. 5b
writes the report with every record change unassessed and the reason. 7a
runs the implementation workflow again on the worktree, then returns to step 5.

## Testing the IDE

- e-unit through elk (`elk test`, see AGENTS.md), per job above, against fixture git repositories
  holding small sets of records.
- A scripted stand-in machine: a small ACP program replaying fixed sessions
  (asks a question, edits a file, finishes, stops early), so sessions and UW-1
  are tested deterministically, without an AI program.
- One end-to-end run against a real AI program before each release, by hand
  at first.
- Tests carry record pointers, per AGENTS.md.

## Packaging, later (ADR-1)

Two prior bundles of Emacs to learn from:

- Lisp in a Box: Emacs plus SLIME plus a Lisp, built not to interfere with an
  existing Emacs installation.
  https://github.com/parkplace/lispbox
- Portacle, its modern successor: a small launcher prepares the runtime
  environment before starting Emacs, and each bundled component has its own
  build script with stages (`download`, `prepare`, `build`, `install`) driven
  by one `build.sh`.
  https://github.com/portacle/portacle/blob/master/build/README.md
